# 基于 B/S 架构的软件测试系统 — 说明与大纲

本文件夹仅存放**毕业设计说明文档与实现大纲**，不修改项目内已有的 YAPI 源码。

---

## 一、项目定位

- **题目**：基于 B/S 架构的软件测试系统设计与实现  
- **目标**：在一个统一的 B/S 平台上，提供**接口测试**与**UI 测试**两大模块。  
- **当前策略**：  
  - **接口测试**：基于 YAPI 开源框架，按需求做功能裁剪与定制。  
  - **UI 测试**：计划采用 Karate 框架，具体形态见下文。

---

## 二、技术栈差异与整合思路

### 2.1 技术栈对比

| 模块     | 选用方案 | 技术栈概要 |
|----------|----------|------------|
| 接口测试 | YAPI     | Node.js + Koa + MongoDB，前端 React，自带接口管理、Mock、简单自动化测试 |
| UI 测试  | Karate   | Java（JVM），BDD 风格 `.feature`，可做 API 测试 + UI 测试（配合 WebDriver） |

二者技术栈不同：YAPI 是独立 Node 应用，Karate 是跑在 JVM 里的测试框架，**不适合**把两套代码直接揉进一个进程。推荐做法是：**统一入口 + 多子系统**。

### 2.2 整体架构思路：统一门户 + 两个子系统

- **统一门户（你的“自己的页面”）**  
  - 一个 B/S 站点，作为唯一入口。  
  - 提供导航：例如「接口测试」「UI 测试」两个主模块入口。  
  - 技术选型可轻量：例如 Vue3/React 单页 + 简单后端（Node 或 Java Spring Boot 二选一），或纯静态 + Nginx 反向代理。

- **接口测试模块**  
  - **直接复用 YAPI**：YAPI 独立部署（如端口 3000），保持其原有技术栈不变。  
  - 在门户中通过以下方式之一“接入”：  
    - **方式 A**：链接跳转 — 点击「接口测试」打开新标签页或同站路径，指向 YAPI 的 URL。  
    - **方式 B**：iframe 嵌入 — 在门户某路由下用 iframe 嵌入 YAPI 页面（需注意登录态/跨域）。  
    - **方式 C**：反向代理 — 门户后端或 Nginx 将 `/api-test/*` 代理到 YAPI 服务，这样同域、可共享 Cookie，体验更统一。

- **UI 测试模块**  
  - Karate 本身是**命令行/JUnit 执行**的测试框架，不是现成的 Web 管理台。  
  - 需要你**额外开发一个“UI 测试管理平台”**：  
    - **后端**：用 Java（如 Spring Boot）提供 REST API，负责：用例管理、执行任务调度、读取 Karate 报告等。  
    - **执行引擎**：在 JVM 内通过 JUnit 或 ProcessBuilder 调用 Karate 运行 `.feature`，将结果写为报告文件或写入数据库。  
    - **前端**：在门户下做「UI 测试」子模块页面，负责：用例列表/编辑、执行、报告展示。  
  - 这样：**门户 + UI 测试管理前后端** 与 **Karate** 同属 Java 技术栈，易于集成；YAPI 保持 Node，通过门户入口和（可选）反向代理与门户统一。

### 2.3 小结：如何“兼容”两种技术栈

- **不强行合并进程**：YAPI 单独跑，UI 测试平台（Java + 前端）单独跑。  
- **在“自己的页面”里统一**：  
  - 门户提供导航与路由；  
  - 接口测试 = 跳转或代理到 YAPI；  
  - UI 测试 = 门户内的子应用（Vue/React 等） + Java 后端 + Karate 执行引擎。  
- **可选统一登录**：若需要，可在门户做一次登录，通过 Token 或 Cookie 下发给 YAPI（需 YAPI 支持或改造）和 UI 测试后端，实现单点登录。

### 2.4 架构示意（逻辑视图）

```

                    │           统一门户 (B/S 入口)              │
                    │   Vue/React 单页 + 导航 + 路由            │
                    └──────────────┬──────────────────────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              │                    │                    │
              ▼                    ▼                    ▼
```

## 三、门户前端交互设计（已确认）

以下为已确定的门户页面形态，便于实现与论文描述一致。

### 3.1 整体布局

- **登录**：进入系统前需登录，门户统一做身份校验。
- **侧边栏导航**：登录后主界面为「侧边栏 + 主内容区」。侧边栏提供 Tab 选项：
  - **接口测试**
  - **UI 测试**
  - （可选）个人中心、退出等

### 3.2 各 Tab 的展示方式（文档 + 入口分离）

- **不采用**：点击侧边栏 Tab 后直接跳转到对应子系统（YAPI 或 UI 测试平台）。
- **采用**：点击某个 Tab 后，**主内容区先展示该模块的使用说明 / 技术文档 / 教程**（如：接口测试模块介绍、如何创建项目与接口、如何执行测试等），**旁边再提供一个明确按钮**（如「进入接口测试平台」「进入 UI 测试平台」），点击该按钮才跳转到对应的服务页面（新开标签或当前页跳转均可）。

这样做的意义：

- 用户先看到**说明与教程**，降低上手成本，也便于答辩时展示“平台配套文档”的完整性。
- **入口按钮**与文档分离，逻辑清晰，避免“一点就跳走”导致不知道平台能做什么；老师也能看到你有**文档设计**和**入口设计**两部分的实践。

### 3.3 小结

| 区域       | 内容 |
|------------|------|
| 登录       | 门户统一登录页，校验通过后进入主界面 |
| 侧边栏     | Tab：接口测试、UI 测试（及可选其他） |
| 主内容区   | 当前选中 Tab 对应的**使用说明/教程/文档** + **进入对应服务的按钮** |
| 真实服务   | 仅通过「进入 xxx 平台」按钮跳转至 YAPI 或 UI 测试平台 |

该设计**合适**，可直接作为需求与实现依据；若后续希望“在门户内嵌 iframe 而不跳转”，可在同一布局下将按钮改为“在同一页内嵌子系统”的交互，文档区保持不变。
