## 题目：基于 B/S 架构的软件测试系统设计与实现

---

## 一、选题背景与意义

### 1.1 选题背景

随着软件规模的扩大和交付节奏的加快，测试工作已成为保障产品质量的关键环节。在企业实践中，**接口测试（API 测试）**与**界面测试（UI 测试）**应用最为广泛：接口测试用于验证服务端接口的正确性、性能与稳定性，UI 测试用于验证用户界面的功能与交互是否符合预期。

笔者在软件测试工程师岗位的两段实习中观察到以下现象：

- **接口测试**：不少团队仍以单接口、单次请求的手工测试为主，难以覆盖依赖登录态、时间戳或上游接口返回值的场景；若使用 Postman 等工具做多接口串联与参数关联，配置复杂、学习成本高，且不利于团队统一管理与沉淀。
- **UI 测试**：校内课程多采用 Selenium 等编写脚本的方式，对编程能力要求高，脚本易因页面改版而失效；企业更期望**无代码或低代码**的可视化方案，降低门槛、减少人为错误，并能与持续集成等流程结合。

因此，本课题拟设计并实现一套**基于 B/S 架构的软件测试系统**，将接口测试与 UI 测试集成于同一 Web 平台，针对上述痛点提出可行方案，并预留向**智能化、可视化**方向扩展的空间（如基于自然语言或视觉描述的 UI 操作）。

### 1.2 研究意义

- **理论层面**：将 B/S 架构与软件测试工程相结合，系统梳理接口测试与 UI 测试在统一平台下的需求、架构与实现路径，为同类系统的设计与教学提供参考。
- **应用层面**：为中小型团队或高校实验室提供一套可部署、易上手的 Web 测试平台；通过可视化与模块化设计，降低接口测试的配置复杂度和 UI 自动化测试的入门门槛；为后续引入“描述所见、描述操作”的 AI 视觉或自然语言交互预留扩展点，具有一定的前瞻性和实用价值。

## 二、国内外研究现状

### 2.1 软件测试与 B/S 架构

软件测试作为软件工程的重要分支，其方法与工具已较为成熟。B/S（Browser/Server）架构将客户端统一为浏览器，服务端集中处理业务与数据，具有部署简单、维护集中、跨平台等优点，被广泛用于各类管理信息系统与在线平台。将测试管理、用例执行与结果展示置于 B/S 架构下，便于团队协作与统一入口，已成为测试平台建设的常见选择。

### 2.2 接口测试工具与平台

当前接口测试领域存在多种形态的工具：**Postman**、**Apifox** 等以桌面或 Web 形式提供接口调试与用例编排，功能强大但多接口关联、动态参数处理往往需要较多配置或脚本；**YAPI**、**Swagger** 等侧重接口文档与 Mock，部分具备简单测试能力；**JMeter** 等侧重性能与脚本化。现有研究多集中在接口自动化框架设计、与 CI/CD 的集成等方面，对“轻量、易用、支持基础动态数据与关联”的一体化 Web 平台仍有需求空间。

### 2.3 UI 自动化测试与低代码/无代码

UI 自动化测试传统上依赖 Selenium、Appium 等框架，通过编写脚本驱动浏览器或移动端进行操作，灵活度高但维护成本和门槛也高。近年来，**低代码/无代码**测试平台逐渐增多，通过录制回放、可视化编排步骤等方式减少手写代码；部分产品开始探索结合**自然语言**或**视觉识别**（如“点击登录按钮”）生成或辅助生成测试步骤。高校与企业对“低门槛、少出错、易维护”的 UI 测试方案需求明确，本课题在实现基础可视化与用例管理的同时，可将“描述性操作”作为后续扩展方向，与上述趋势相衔接。

### 2.4 小结

综合来看，将接口测试与 UI 测试整合在统一 B/S 平台中，并针对动态数据、关联复杂、脚本门槛高、维护成本大等问题进行针对性设计，既有现实需求，也与当前测试工具“平台化、可视化、智能化”的发展方向一致。本课题在此背景下开展系统设计与实现研究，具有可行性与一定创新空间。

## 三、研究内容与目标

### 3.1 研究内容

1. **需求分析**  
   结合实习经历与文献调研，明确软件测试系统在接口测试与 UI 测试方面的功能需求（如项目与接口管理、请求执行与断言、UI 用例管理与执行、报告查看等）以及非功能需求（如 B/S 架构、用户认证、易用性等）。

2. **系统总体设计**  
   基于 B/S 架构进行总体设计：明确浏览器端（前端）与服务端（后端）的职责划分；设计用户认证与权限、接口测试、UI 测试等模块的组成与交互；完成核心数据模型与数据库设计、主要 REST 接口设计。

3. **接口测试模块的设计与实现**  
   实现接口（API）的增删改查及按项目归类；支持配置请求方法、URL、请求头与请求体；实现单接口执行与响应展示，并支持简单断言（如 HTTP 状态码、响应体字段）的配置与校验，为后续扩展动态参数与接口关联奠定基础。

4. **UI 测试模块的设计与实现**  
   实现 UI 测试用例的创建、编辑、删除与执行；以可视化、低代码方式支持用例的编排与运行，降低对编程的依赖；实现执行记录的保存与报告展示；在时间与条件允许时，可对“基于描述的操作”或与视觉/自然语言结合的交互方式进行初步探索或预留接口。

5. **系统集成、测试与总结**  
   完成前后端联调与部署说明，进行基本功能测试；撰写毕业论文，总结设计思路、实现过程、不足与展望。

### 3.2 研究目标

- 完成一个可运行、可演示的 B/S 架构软件测试系统，包含用户登录、接口测试与 UI 测试两大功能模块。
- 接口测试模块支持多项目、多接口的管理与单接口执行及简单断言，解决“单点测试、配置分散”的常见问题。
- UI 测试模块支持用例的可视化/低代码管理与执行，降低自动化测试门槛，并为后续智能化扩展预留空间。
- 形成完整的需求分析、系统设计与实现文档，满足毕业论文（设计）的规范与答辩要求。

## 四、研究方法与技术路线

### 4.1 研究方法

- **文献研究法**：查阅软件测试、B/S 架构、接口测试与 UI 自动化测试相关教材、论文与行业资料，为需求分析与系统设计提供依据。
- **需求分析法**：结合实习经历与调研，归纳接口测试与 UI 测试的痛点与需求，形成功能清单与用例描述。
- **工程实现法**：采用前后端分离的 B/S 架构，选用成熟技术栈进行开发与实现，通过迭代完成各模块并集成测试。

### 4.2 技术路线

- **架构**：B/S 架构；浏览器端负责页面展示与用户交互，服务端负责业务逻辑、认证鉴权与数据持久化。
- **前端**：采用 Vue.js 构建单页应用（SPA），实现登录、侧边栏导航、接口测试与 UI 测试的界面及与后端的 API 调用。
- **后端**：采用 Java + Spring Boot 提供 RESTful API，实现用户认证（如 JWT）、接口测试（项目/接口 CRUD、请求执行与断言）、UI 测试（用例管理、执行调度与报告）等逻辑。
- **数据层**：采用 MySQL 存储用户、项目、接口、断言、UI 用例及执行记录等；UI 测试报告可存路径或文件存储。
- **UI 测试执行**：可选用成熟框架（如 Karate、Selenium）作为执行引擎，由后端调度并汇总结果，前端负责展示；后续若扩展“描述性操作”，可在此基础上增加自然语言或视觉解析模块的接口。

技术路线可概括为：**需求分析 → 总体设计（架构、数据库、接口）→ 后端开发 → 前端开发 → 联调与测试 → 论文撰写与答辩**。
