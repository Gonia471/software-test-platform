## 一、课题名称

基于 B/S 架构的软件测试系统设计与实现

---

## 二、选题背景与意义

### 2.1 背景

软件质量保障离不开系统化的测试工作，其中**接口测试（API 测试）**与**界面测试（UI 测试）**是当前企业中最常用的两类测试手段。笔者在软件测试工程师岗位的两段实习经历中发现，企业内部的测试工具与流程存在以下问题：

- **接口测试方面**：多数环境仅支持单接口、单次请求的手工验证，难以应对依赖**动态数据**（如 token、时间戳、上下游接口返回值）的链路场景；若采用 Postman 等工具做接口关联与参数传递，配置复杂、维护成本高，对测试人员的技术门槛要求也较高。
- **UI 测试方面**：高校教学与实践中多采用 Selenium 等脚本化方案，编写与维护自动化脚本对编程能力要求高，且容易因页面变更导致用例失效；企业需要的是**低门槛、少出错**的测试方式，最好能通过**可视化、无代码**的方式完成用例设计与执行。

因此，设计并实现一套**统一的、以 B/S 架构为基础的软件测试系统**，将接口测试与 UI 测试整合在同一 Web 平台中，并针对上述痛点进行改进，具有明确的现实需求和一定的应用价值。

### 2.2 意义

- **理论意义**：结合 B/S 架构与软件测试工程实践，梳理接口测试与 UI 测试在统一平台下的需求分析与系统设计方法，为同类测试平台的设计与实现提供参考。
- **实践意义**：为中小团队或校内实践提供一套可部署、易使用的 Web 测试平台；接口测试模块支持项目与接口管理、请求调试及简单断言，便于处理多接口与基础动态数据；UI 测试模块以**可视化、低代码/无代码**为方向，降低自动化测试的入门门槛，并可为后续引入**基于自然语言或视觉的智能操作描述**（如“点击登录按钮”）预留扩展空间，提升测试效率与可维护性。

## 三、主要任务与目标

### 3.1 总体目标

设计并实现一个基于 B/S 架构的软件测试系统，在统一 Web 端完成用户认证与权限管理，提供**接口测试**与**UI 测试**两大功能模块，满足日常接口调试、简单自动化接口测试以及 UI 自动化测试的需求。

### 3.2 主要任务

1. **需求分析**：调研企业及高校在接口测试、UI 测试中的常见痛点（单点测试、动态数据、关联复杂、脚本门槛高等），明确系统的功能需求与非功能需求。
2. **系统设计**：完成 B/S 架构下的总体设计，划分浏览器端（客户端）与服务端职责；设计用户与权限、接口测试（项目/接口/断言）、UI 测试（用例/执行/报告）等核心模块的数据库与接口。
3. **接口测试模块实现**：实现接口（API）的创建、编辑、删除及按项目归类；支持自定义请求方法、URL、请求头与请求体；支持单接口执行与结果展示，并支持简单断言（如状态码、响应体字段）的配置与校验。
4. **UI 测试模块实现**：实现 UI 测试用例的管理与执行流程；以可视化、低代码方式支持用例的编排与运行，降低对编程的依赖；支持执行结果的记录与报告查看。
5. **系统集成与测试**：完成前后端联调、部署说明及基本功能测试，保证系统可运行、可演示。

### 3.3 可选扩展（视时间与条件）

- 接口测试：对动态参数（如 token、变量）的简单支持，或接口间的数据关联。
- UI 测试：探索基于自然语言或“所见即所测”的交互方式（如描述“点击登录按钮”），为 AI 视觉融合预留接口或原型。

## 四、工作内容与要求

### 4.1 工作内容

- 查阅与软件测试、B/S 架构、接口测试与 UI 自动化测试相关的文献与资料。
- 完成需求分析文档、系统总体设计（含架构图、模块划分、数据库设计、主要接口说明）。
- 选用合适的技术栈（如前端 Vue、后端 Spring Boot、数据库 MySQL）完成开发与实现。
- 撰写毕业论文（设计）正文，包含选题背景、需求分析、系统设计、实现与测试、总结与展望等章节。
- 按学院要求完成文献综述、外文翻译等材料，并参加答辩。

### 4.2 要求

- 系统采用 B/S 架构，浏览器端负责展示与交互，服务端负责业务逻辑与数据持久化，职责清晰、文档可体现。
- 接口测试与 UI 测试均需有可演示的功能，数据与状态持久化到数据库或文件。
- 论文结构完整、表述清晰、图表规范，引用与参考文献符合学术规范。
- 按时提交任务书、开题报告、文献综述、外文翻译、正文等各阶段材料。
