# 方案选型说明：YAPI 改造 vs 从零自研

本文档对比两种实现路径，并从**毕设通过率、答辩观感、论文可写性、工作量与风险**等角度给出选择建议。**仅作说明与建议，不执行任何代码修改。**

---

## 一、两种方案简述

### 方案 A：基于 YAPI 改造

- **做法**：以现有 YAPI 为底座，在其上做二次开发。
  - 修改页面布局、样式、菜单结构，使之与门户风格一致。
  - **删除或替换所有「YAPI」字样与品牌**，改为本系统名称（如「软件测试平台 - 接口测试」）。
  - 按需求裁剪冗余功能（如部分插件入口、统计页等），保留：接口管理、调试、Mock、自动化测试等核心能力。
  - 门户通过侧边栏 Tab + 使用说明 + 入口按钮，跳转或代理到改造后的「接口测试」服务。
- **技术栈**：门户（如 Vue + Node/Java）+ YAPI（Node + Koa + MongoDB + React）+ UI 测试（Java + Karate），**多技术栈并存**。

### 方案 B：从零自研接口测试模块（统一技术栈）

- **做法**：不再使用 YAPI 作为运行时，**自己从零设计并实现**接口测试相关功能。
  - 接口测试的：项目/分组管理、接口定义、请求调试、简单自动化测试（如断言）、Mock（可选）等，全部在自己的项目里用**同一套技术栈**实现。
  - 门户与接口测试、UI 测试管理共用同一前端框架与后端语言（例如全栈 Vue + Java Spring Boot，或全栈 Vue + Node）。
  - 仅「UI 测试执行引擎」仍可采用 Karate（Java），与后端同属 JVM，集成简单。
- **技术栈**：**统一为一套**（如 Vue + Spring Boot + MySQL/PostgreSQL），Karate 仅作为测试运行时被后端调用，不暴露为独立系统。

## 二、对比维度

| 维度 | 方案 A：YAPI 改造 | 方案 B：从零自研 |
|------|-------------------|------------------|
| **答辩观感** | 易被理解为「套壳/套皮」，若改造点说不清，可能被认为实践不足 | 前后端、数据库、接口设计均为自研，容易讲清「自己做了什么」 |
| **论文可写性** | 需重点写「需求分析与裁剪」「YAPI 架构分析与改造设计」「与门户的集成」；若改造不深，章节容易单薄 | 可写：需求分析、系统架构、数据库设计、接口设计、核心模块实现、测试与总结，章节饱满 |
| **工作量与周期** | 改造与去品牌化有现成代码可依，周期相对可控；但要吃透 YAPI 源码才能改得有理有据 | 从零开发接口管理+调试+测试，工作量更大，需合理控制功能范围（如先不做 Mock，先做核心 CRUD+调试+简单断言） |
| **技术栈复杂度** | Node（YAPI）+ 门户可能 Node/Java + Java（UI 测试），多栈，部署与文档都要写多套 | 单一技术栈，部署、环境、论文中的「技术选型」更清晰 |
| **创新与价值体现** | 价值主要体现在「业务定制、集成与裁剪」，若改造点明确、文档清晰，仍可过关 | 价值体现在「完整系统设计能力」「从 0 到 1 的实现」，更容易体现个人能力 |
| **风险** | 若老师追问「哪些是你写的、哪些是 YAPI 自带的」，若答不细可能扣分 | 功能范围若贪大容易做不完，需做 MVP 规划 |

## 三、选择建议

### 若更看重「稳妥通过 + 控制工作量」

- **选方案 A（YAPI 改造）**更合适。
- **必须做到**：
  - 彻底去除 YAPI 品牌与字样，替换为自拟系统名称与 Logo。
  - 在副本/分支上做改造，列出**改造清单**（改了哪些页面、删了哪些菜单、如何与门户对接），在论文和答辩中专门用一小节/一页说明「基于开源框架的定制化设计」与「本人完成的工作」。
  - 门户侧按前文设计：登录 + 侧边栏 + 使用说明 + 入口按钮，体现「统一入口与文档」是你独立设计的。

这样既能借助 YAPI 减少从零造轮子的时间，又能通过**去品牌 + 改造清单 + 门户与文档设计**体现实践量，降低「纯套皮」的观感。

### 若更看重「论文好写、答辩好讲、技术栈统一、价值感强」

- **选方案 B（从零自研）**更合适。
- **建议**：
  - 接口测试模块做 **MVP**：先做「项目 → 接口 CRUD → 单接口请求调试 → 简单响应断言」，再视时间加 Mock 或批量测试。
  - 前后端统一技术栈（如 Vue3 + Spring Boot + MySQL），UI 测试管理后端也用同一套，仅 Karate 作为 JVM 内执行引擎；论文里「技术选型」一章会非常干净。
  - 把「从 0 设计数据库、API、前端页面」的过程写进论文，答辩时按模块讲「自己如何设计、如何实现」，说服力强。

缺点是开发量明显大于方案 A，需要你根据截止时间与个人时间评估是否可行。

### 折中思路（若时间紧张又希望减少「套皮」感）

- 采用**方案 A**，但**刻意加大「自研比例」**：
  - 门户、登录、侧边栏、使用说明与入口按钮、统一权限（若做）**全部自研**。
  - 对 YAPI 只做「最小嵌入」：入口按钮跳转到改造后的 YAPI，YAPI 仅保留核心的接口管理与测试，其余全部删减，并**在论文中单独画一张「YAPI 架构与裁剪图」**，说明你删除了哪些、保留了哪些、为何这样裁剪。
  - 这样答辩时可以强调：「整体架构、门户、文档、入口与集成方案均为本人设计；接口测试能力基于某开源框架做了深度裁剪与去品牌化改造」，实践点更清晰。

## 四、与门户设计的衔接

无论选 A 还是 B，**门户前端交互**保持一致（见 README「门户前端交互设计」）：

- 登录后：侧边栏 Tab「接口测试」「UI 测试」。
- 点击 Tab：主内容区展示**该模块的使用说明/技术文档/教程**，旁边有**入口按钮**。
- 点击「进入接口测试平台」：  
  - 方案 A → 跳转至改造后的 YAPI（已去品牌）。  
  - 方案 B → 跳转至自研的接口测试前端（同域或子路径）。
- 点击「进入 UI 测试平台」：跳转至 UI 测试管理前端（用例、执行、报告）。

两种方案下，**使用说明与入口按钮**均可复用同一套门户页面结构，仅跳转目标不同。

## 五、文档与论文中的表述建议

- **方案 A**：在论文中可设小节如「基于 YAPI 的接口测试模块定制」「开源框架选型与裁剪设计」「去品牌化与界面统一」，并附改造前后对比或改造清单表。
- **方案 B**：在论文中可设小节如「接口测试模块需求分析」「接口测试模块架构与数据库设计」「核心接口与前端实现」，突出「自研」与「统一技术栈」。

最终选择可根据：**答辩时间、个人编码时间、学校对「使用开源」的接受程度**综合决定；若学校明确鼓励「尽量自研」，可优先考虑方案 B 或折中思路。
