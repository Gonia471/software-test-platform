# 基于 B/S 架构的软件测试系统 — 实现大纲

本文档给出分阶段实现步骤与可交付物，便于按顺序推进毕设。**YAPI 源码暂不修改**，先完成门户与整体集成设计。

---

## 一、阶段划分总览

| 阶段 | 内容概要 | 主要产出 |
|------|----------|----------|
| 阶段一 | 需求与总体设计 | 需求说明、架构图、数据库/接口概要 |
| 阶段二 | 统一门户与接口测试入口 | 门户站点、对接/集成 YAPI |
| 阶段三 | YAPI 定制（可选） | 需求裁剪、冗余功能删除、必要改造 |
| 阶段四 | UI 测试平台设计与实现 | Karate 集成、用例管理、执行与报告 |
| 阶段五 | 联调与论文/答辩 | 整体演示、文档、答辩材料 |

---

## 二、阶段一：需求与总体设计

### 2.1 工作内容

- 明确「接口测试」必须保留的 YAPI 功能（如：接口管理、运行、Mock、简单自动化测试等），列出拟删除或弱化的功能。
- 明确「UI 测试」范围：用例管理、执行方式（单次/批量）、报告展示、是否与接口测试共享项目等。
- 画出系统架构图：门户 → 接口测试（YAPI）→ UI 测试平台（Java + Karate）。
- 定义门户与各子系统的角色、权限（若需要）。
- 数据库：YAPI 沿用 MongoDB；UI 测试平台可选用 MySQL/PostgreSQL + 表结构设计（用例、执行记录、报告路径等）。

### 2.2 可交付物

- 需求规格说明（或章节）
- 总体架构图（可放毕设文档）
- 接口测试 / UI 测试 功能清单
- （可选）数据库 ER 图或表结构说明

## 三、阶段二：统一门户与接口测试入口

### 3.1 门户交互形态（与 README 一致）

- **登录**：门户统一登录，通过后再进入主界面。
- **主界面**：侧边栏 + 主内容区。侧边栏为 Tab：「接口测试」「UI 测试」等。
- **各 Tab 行为**：点击 Tab 后，**主内容区不直接跳转到子系统**，而是先展示**该模块的使用说明 / 技术文档 / 教程**（如接口测试介绍、操作步骤等），**主内容区旁提供明显按钮**（如「进入接口测试平台」「进入 UI 测试平台」），用户点击该按钮后才跳转到对应服务页面（新开标签或当前页跳转均可）。

### 3.2 工作内容

- **搭建统一门户**  
  - 技术选型：如 Vue3 + Vue Router + 简单 Node/Java 后端，或纯静态 + Nginx。  
  - 实现：登录页、登录后侧边栏导航（接口测试、UI 测试）、各 Tab 对应的「使用说明/文档」页面与「进入 xxx 平台」按钮。

- **集成接口测试能力**（具体取决于 [方案选型说明](./方案选型说明.md)）  
  - **若采用 YAPI 改造**：部署 YAPI（或改造副本），门户「进入接口测试平台」按钮跳转或代理到 YAPI。  
  - **若采用从零自研**：该按钮跳转到自研的接口测试前端（同域子路径或独立路由）。  
  - 若需统一登录，再考虑与子系统的 Token/Cookie 对接（可放在阶段三或自研模块中实现）。

### 3.3 可交付物

- 可运行的统一门户（登录 + 侧边栏 + 各 Tab 的说明文档 + 入口按钮）。
- 点击「进入接口测试平台」能到达接口测试服务（YAPI 或自研）。
- 简要部署/运行说明。

---

## 四、阶段三：接口测试模块的最终形态（二选一）

本阶段取决于 [方案选型说明](./方案选型说明.md) 中的选择。

### 4.1 若选择「YAPI 改造」

- 在**副本**或**分支**上对 YAPI 做修改，避免污染原始 `yapi-master`。  
- **去除所有 YAPI 品牌与字样**，替换为本系统名称。  
- 按阶段一清单：删除或隐藏冗余菜单/功能（如不需要的插件入口、统计等）。  
- 若门户与 YAPI 需统一风格：可调整 YAPI 前端主题或仅改门户样式，使视觉一致。  
- 若需单点登录：研究 YAPI 登录扩展或 Token 校验，与门户登录对接。  
- **可交付物**：定制后的 YAPI 版本（或补丁说明）、功能裁剪与去品牌清单（便于毕设文档与答辩说明本人工作）。

### 4.2 若选择「从零自研」

- 本阶段改为**自研接口测试模块**：项目/分组管理、接口定义、请求调试、简单自动化测试（断言）等，与门户统一技术栈。  
- 门户「进入接口测试平台」按钮指向自研前端，不再依赖 YAPI。  
- **可交付物**：自研接口测试前后端、数据库设计、接口文档；论文中可重点写需求分析、架构与实现。

---

## 五、阶段四：UI 测试平台（Karate 集成）

### 5.1 工作内容

- **后端（Java）**  
  - 使用 Spring Boot 搭建 REST API。  
  - 用例管理：CRUD、与「项目」或「模块」关联（可与 YAPI 项目概念对齐，便于论文表述）。  
  - 执行服务：调用 Karate 执行指定用例或套件（JUnit Runner 或 `Runtime.getRuntime().exec` 调 `mvn test`/`gradle test`），将结果解析入库或写文件。  
  - 报告：将 Karate 生成的 HTML/JSON 报告路径存库，并提供接口给前端展示或下载。

- **Karate 侧**  
  - 搭建 Karate 工程（Maven/Gradle），编写示例 UI 测试（如 Karate + WebDriver）。  
  - 约定用例与 ID 或路径的对应关系，便于后端按“用例”触发执行。

- **前端（门户内子模块）**  
  - 在门户下增加「UI 测试」路由与页面。  
  - 功能：用例列表、新增/编辑（或仅上传 `.feature`）、执行、报告查看（iframe 或新开页链接到报告 HTML）。

### 5.2 可交付物

- UI 测试管理后端（Spring Boot）+ 数据库表与接口文档。
- Karate 示例用例与执行方式说明。
- 门户内 UI 测试子模块（列表、执行、报告）。

## 六、阶段五：联调与论文/答辩

### 6.1 工作内容

- 门户、YAPI、UI 测试平台联调：从门户可完整走通「接口测试」与「UI 测试」流程。  
- 整理部署文档：环境要求、启动顺序、端口、反向代理配置等。  
- 撰写毕设论文/报告：需求、架构、接口设计、实现、测试、总结。  
- 准备答辩演示：从统一入口进入两大模块并演示核心功能。

### 6.2 可交付物

- 可演示的完整系统。
- 毕设论文/报告与答辩材料。

---

## 七、建议开发顺序（时间线）

1. **先做阶段一、二**：确定方案选型（YAPI 改造 vs 从零自研）后，把门户搭起来（登录 + 侧边栏 + 各 Tab 使用说明 + 入口按钮），并让「进入接口测试平台」指向对应服务（YAPI 或自研），形成统一入口雏形。  
2. **再做阶段四的骨架**（UI 测试）：后端 + 简单前端 + 最少 1 个 Karate 用例，能执行并看到报告；门户「UI 测试」Tab 的说明 + 入口按钮指向该模块。  
3. **然后做阶段三**：若选 YAPI 改造则做裁剪与去品牌；若选从零自研则完成自研接口测试模块。  
4. **最后阶段四完善 + 阶段五**：完善 UI 测试功能、联调、写文档与答辩。

## 八、技术选型速查

| 部分           | 方案 A（YAPI 改造） | 方案 B（从零自研） |
|----------------|---------------------|---------------------|
| 统一门户前端   | Vue 3 + Vue Router（或 React） | 同上，与接口测试可共用 |
| 门户后端（若需要） | Node 或 Java (Spring Boot) | 与接口测试共用同一后端 |
| 接口测试       | YAPI（Node + Koa + MongoDB + React），改造并去品牌 | 自研（与门户同栈，如 Vue + Spring Boot + MySQL） |
| UI 测试执行    | Karate (Java) | 同上 |
| UI 测试管理后端 | Java + Spring Boot | 与门户/接口测试可同后端 |
| UI 测试管理前端 | 与门户统一（Vue/React） | 同上 |
| 反向代理       | 可选：Nginx 或后端代理到 YAPI | 通常不需要，同域即可 |
